# 部署指南

本指南假设：主源是**你的服务器**（Nginx/OpenResty 反代到 Docker），备用是**同一应用的另一个 Cloudflare Worker**（数据层共享 D1/KV 时接管无缝）。

完整链路：

```
用户 → cf-edge-router（边缘）→ 回源主源（灰云子域 → 服务器 → Docker）
                             └→ 备用 Worker（主源异常时）
```

## 第 1 步：创建 KV namespace

```bash
npx wrangler kv namespace create ROUTER_STATE
```

把返回的 `id` 填入 `wrangler.toml` 的 `[[kv_namespaces]]`。

## 第 2 步：配置 [vars]

按你的场景修改 `wrangler.toml`：

| 变量 | 示例 | 说明 |
|------|------|------|
| `DOCKER_ORIGIN` | `http://origin.example.com` | 灰云子域（见第 3 步） |
| `DOCKER_HOST` | `www.example.com` | 回源 Host 头 |
| `FALLBACK_WORKER` | `https://app.example.workers.dev` | 备用 Worker |

## 第 3 步：灰云 DNS 记录（关键，官方硬性要求）

**Workers 子请求禁止 fetch 裸 IP（error 1003），也禁止 fetch 代理（橙云）域名（会绕回 CF 网络被拦）。** 必须为源站 IP 创建一条 **DNS-only（灰云）** A 记录：

1. Cloudflare Dashboard → 域名 → DNS → Records → Add record
2. Type `A`、Name `origin`、IPv4 `你的服务器IP`
3. **Proxy status 必须选 DNS only（灰色云朵）** —— 不要橙云
4. Save

> 公共 DNS 查询该记录会看到 Cloudflare 的占位 IP（如 `28.0.0.50`），这是正常的对外隐藏机制；CF 内部解析器（Worker fetch）会拿到真实 IP。

## 第 4 步：主源服务器配置 server_name（否则 404）

Worker 回源时发到源站的 Host 头是灰云子域（如 `origin.example.com`），Nginx/OpenResty 需认识它并转发到对应站点：

```nginx
server {
    listen 80;
    server_name origin.example.com;
    include /www/sites/www.example.com/proxy/*.conf;  # 复用主站的反代配置
}
```

保存后 reload：`sudo nginx -s reload`（或 1Panel 面板点应用）。

## 第 5 步：部署与验证

```bash
npx wrangler deploy
```

验证（不接管线上流量，先走 workers.dev 域名）：

```bash
curl https://cf-edge-router.<your-subdomain>.workers.dev/api/health
# 期望返回主源应用的响应（2xx）
```

> 此时若返回 404：检查第 4 步的 server_name；返回 1003：检查第 3 步是否灰云。

## 经验与踩坑记录（生产验证过）

### 1. 主源 server_name 推荐用"多域名"而非独立 server 块

Worker 回源时发到源站的 Host 头是灰云子域（如 `origin.example.com`）。**最省事的做法**是主站 server block 直接加一个名字，而不是复制整个 server 块：

```nginx
server {
    listen 80;
    server_name www.example.com origin.example.com;  # ← 加灰云子域即可
    include /www/sites/www.example.com/proxy/*.conf;
}
```

### 2. 部署后短暂 404？等 Cron 跑一轮

router 的 fallback 决策依赖 KV 健康状态。**首次部署 / 改回源目标后，KV 可能残留旧的 `down` 状态**（或 Cron 尚未探测），导致请求短暂走 fallback（表现是 workers.dev 域名返回备用 Worker 或 404）。等 Cron（1 分钟）把健康状态更新为 `up` 后自动恢复。排查看 router 日志：`npx wrangler tail <worker>`，`[cf-edge-router] 回源响应: 200` 即正常。

### 3. nginx 对"未知 Host"返回 404（default_server）

直连源站时若 Host 头不是任何 server_name（如被替换为 IP），nginx 走 default_server 返回 404。**排查法**：`curl -H "Host: <灰云子域>" http://<源站IP>/api/health` 分别测 `Host=<子域>` 与 `Host=<IP>`，前者应 2xx。本方案依赖 server_name 匹配，务必做第 4 步/经验 1。

### 4. routes 必须放 wrangler.toml 顶层

`routes` 若写在 `[triggers]` 段之后，TOML 会把它归入 triggers，wrangler 告警 `Unexpected fields found in triggers field: "routes"` 且路由不生效。**routes 放顶层**（kv_namespaces/triggers 之前）：

```toml
name = "cf-edge-router"
main = "worker.js"
compatibility_date = "2025-07-15"
routes = [
  { pattern = "www.example.com/*", zone_name = "example.com" }
]
# ... 其他段
```

验证绑定：Cloudflare API `GET /zones/<zone_id>/workers/routes`（pattern + script 字段）。

### 5. curl/无头浏览器被 Cloudflare 质询属正常

若 zone 开启了 Bot Fight / Managed Challenge，curl 与无头浏览器访问**橙云代理域名**会返回 403 质询页（`Just a moment...` / Turnstile）。**真实浏览器用户不受影响**。验证线上链路请用真实浏览器，或用 workers.dev 域名（不经 zone 质询层）。

### 6. 同 zone Worker 之间禁止 fetch()（error 1042）——用 Service Binding

fallback 目标如果是**同一个 Cloudflare zone 下的另一个 Worker**（如 `xxx.workers.dev` 同账号/同域名），直接 `fetch()` 会报 **error 1042**（"Worker tried to fetch from another Worker on the same zone"）。**正解**：wrangler.toml 配 `[[services]]`（Service Binding），代码里 `env.FALLBACK.fetch(request)` 直调，免费计划支持、无 1042。

```toml
[[services]]
binding = "FALLBACK"
service = "your-backup-worker"
```

### 7. request body 只能消费一次 —— 回源与 fallback 都要用 request.clone()

POST 请求的 body 是流，**回源 fetch 消费后，fallback 再复用同一个 request 会抛** `Cannot reconstruct a Request with a used body`。回源和 fallback 必须各自 `request.clone()`：

```js
// 回源
await fetch(buildUpstreamRequest(request.clone(), target, host));
// fallback
return await env.FALLBACK.fetch(request.clone());
```

### 8. 健康状态 TTL 必须大于 Cron 间隔（防过期竞态）

Cron 每 60s 探测一次，若 `HEALTH_TTL_SEC = 60` 恰好等于间隔，调度抖动会导致 KV 长期处于"刚过期"的竞态（router 侧读不到状态、wrangler API 查询 also not found）。**TTL 设 120s**（大于间隔即可）。

> 另注意：**wrangler kv key get 查不到刚写入的 key 不一定是没写入**——KV 是最终一致，Worker binding 在边缘写入后 API 读可能有传播延迟。确认写入是否成功用 `wrangler tail` 看 scheduled 日志（探针日志）更可靠。

## 第 6 步：接管流量（最后一步，确认无误后启用）

在 `wrangler.toml` 取消 `routes` 注释，填入你的域名：

```toml
routes = [
  { pattern = "www.example.com/*", zone_name = "example.com" }
]
```

重新部署后，该域名的全部流量先进 cf-edge-router，按健康状态分流。

> 注意：接管后 `www.example.com` 会变成"先到调度器再回源"，主源服务器只需保持第 4 步的配置（回源请求直接经灰云子域进入）。

## 灰度玩法

- 纯容灾：`WEIGHT_DOCKER = "100"`（全走主源，故障自动切备用）
- 灰度发布：`WEIGHT_DOCKER = "95"`（5% 流量到备用 Worker 验证新版本，逐步下调回 100）
- 权重改后无需重新部署（v2 将支持 KV 动态配置）

## 故障演练

1. 停掉主源 Docker：`sudo docker stop <container>`
2. 等 1-2 分钟（Cron 探测周期）
3. 访问网站 → 应正常由备用 Worker 接管（数据层共享则无感）
4. 启动 Docker → 1-2 分钟后自动切回
